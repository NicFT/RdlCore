# Platform support

## Current status

The new rendering abstractions are intended to support a gradual migration away from Windows-only assumptions. At the moment the work is best thought of as a compatibility layer rather than a complete cross-platform rewrite.

## Supported areas

## Known gaps

- The broader reporting pipeline still contains legacy Windows-specific assumptions in other paths.
- **RDL 2005 upgrade path** (`Microsoft.ReportingServices.RdlObjectModel2005.Upgrade/UpgradeImpl2005.cs`, run at compile time for any `.../reporting/2005/01/reportdefinition` report): `ReportSize.DotsPerInch` used to create a GDI+ `Bitmap` and crashed compiling every 2005 report on Linux (`DllNotFoundException: gdiplus.dll`); fixed 2026-10-19 by returning a constant 96 (`AdjustBodyWhitespace` round-trips sizes through pixels, so the DPI cancels out). Still open: `UpgradeImpl2005.FontFromString` uses `FontConverter`/`new Font(...)` and will fail the same way for 2005 reports that contain Dundas chart/gauge custom report items (`DundasChartControl`/`DundasGaugeControl`). Workaround: re-save the report in a current Report Designer so it is no longer 2005-schema.
- Full fidelity for complex Excel or PDF layouts is not yet guaranteed.
- Additional renderers and output formats should be introduced behind the same abstraction pattern.

## Chart, Gauge, and Map rendering (GDI+)

There are **three separate, parallel GDI+-coupled rendering engines** in the solution, not one: Chart (`Microsoft.Reporting.Chart.WebForms`), Gauge (`Microsoft.Reporting.Gauge.WebForms`), and Map (`Microsoft.Reporting.Map.WebForms`). Chart and Gauge are actively being migrated to the Ports & Adapters design in `docs/rendering-abstractions.md`; Map's migration is deferred (LOW priority, scheduled after PDF Phase 1 — see `docs/decisions.md`), since its built-in Bing Maps tile-layer integration is independently end-of-lifed for RDL/RDLC consumers.

| Area | Windows | Linux/macOS | Notes |
| --- | --- | --- | --- |
| Chart rendering (2D) | Yes | Yes (2026-07-31) | `ChartRenderingBackendFactory` selects Skia by platform for the real `ChartMapper.GetImage`→`Chart.Save`→`ChartImage.SaveImage` path. The former default-`Font`-construction wall (any chart needing a real, never-explicitly-set default `Font` for measurement, e.g. `Legend.GetOptimalSize`) is fixed — a 6-fix chase (`tasks/chart-default-font-cross-platform.md`) resolved every construction-time crash on the path to a real chart (Legend, PieChart/Sunburst map areas, DataPointAttributes fonts) plus the IMAGE renderer's own `GetScreenDpi`, WSL-verified end to end with a rendered, visually-correct chart |
| Chart rendering (3D) | Yes | Yes (2026-07-31) | Same fix set as 2D above applies — the `IGraphicsPath`/backend-selection work plus the default-Font chase cover 3D scenes with a Legend the same way |
| Gauge rendering | Yes | No | GDI+→interface abstraction is complete; no Skia (or other second) backend exists yet — never started, low priority, not scheduled. Object construction no longer crashes either (2026-07-28 fix), but rendering itself is still 100% GDI+ regardless. See "Gauge Skia backend" gap below for the expected shape |
| Map rendering | Yes* | No | Deferred, LOW priority (after PDF Phase 1) — see `docs/decisions.md`; Bing Maps tile integration is end-of-lifed regardless, a Google Maps/OpenStreetMap adapter would be a prerequisite decision. *A functional bug independent of platform was found 2026-07-31: RDL-defined Map layers (data-bound or static) never actually populate any spatial elements (`SpatialDataSetMapper.ProcessRow`/`EmbeddedSpatialDataMapper.AddSpatialElement`/`VectorLayerMapper.CreateSpatialElementFromDataRegion` are all empty/dead-code stubs) — a Map with only borders/titles/legends renders, but one with actual point/polygon/line data does not. See `tasks/map-spatial-data-population-gap.md` |
| Chart Skia backend | N/A | Wired into production | `ChartRenderingBackendFactory` selects it by platform for both `ChartPicture.renderSurfaceFactory` and `chartGraph`; `IRenderSurface.DrawBackgroundBorder` removed the last hard `GdiRenderSurface` downcast from `ChartImage.SaveImage`. |

**Fundamental blocker (confirmed by a Phase 0 spike, 2026-07-18):** GDI+ cannot construct *any* `System.Drawing` object at all on Linux under .NET 10 — not even a bare `Font`/`Pen`/`Bitmap` — even with `libgdiplus` installed. This no longer blocks Chart rendering itself (Milestone F routes the real production path through Skia on non-Windows instead), but still applies to anything that hasn't been ported behind the Skia backend (Gauge, Map, `ChartImage.GetImage`'s `Bitmap` contract below) — **and, discovered 2026-07-28, still applies to the Chart/Gauge model classes' own default `Font` values**, wherever real (never explicitly overridden) font metrics are actually needed for measurement rather than just storage. See `docs/decisions.md`'s "Chart/Gauge model classes could not even be constructed" entry and `tasks/chart-default-font-cross-platform.md`.

**`ChartImage.GetImage(float) : Bitmap`'s declared return type is itself a hard, external, GDI+-typed public API contract, permanently unfixable** — even a complete Skia backend must still produce a `System.Drawing.Bitmap` to satisfy it, which GDI+'s Linux construction gap (above) makes impossible today. This is a distinct, permanent wall, separate from `Chart.Save`'s path: `ChartMapper.GetImage` calls `Chart.Save(Stream, ChartImageFormat)`, which never returns a `Bitmap` and already routes through `IRenderSurface.Encode`/`DrawBackgroundBorder` — the *reachable* production path has no `Bitmap`-contract wall at all, and Milestone F wired its platform selection. Don't conflate the two: `GetImage`'s wall is permanent; `Chart.Save`'s path is fully cross-platform now.

### Known permanent/architectural gaps (no cross-platform equivalent attempted)

- **Metafile/EMF export** (`ChartImage.SaveIntoMetafile`) — needs a raw Windows HDC (`Graphics.GetHdc()`); intrinsically Windows-only, guarded rather than ported.
- **`Pen.CustomStartCap`/`AdjustableArrowCap`** (custom arrow-shaped line caps) — one Chart site (`SmartLabels.cs`'s `DrawCallout`), no Skia equivalent; left concrete, low priority/cosmetic.
- **`GraphicsPathIterator`** (subpath/compound-path iteration) — no interface or Skia equivalent. Chart's `CalloutAnnotation.cs` worked around this with a hand-rolled `SplitAtMarkers` helper reading `IGraphicsPath.PathTypes`'s marker bits directly, rather than depending on the GDI+-only iterator type.
- **`GraphicsState`** (opaque snapshot from `Graphics.Save()`/`Restore()`) — no interface-typed equivalent exists anywhere in the port; found in `LineChart.cs`'s shadow-line block, not yet investigated further.
- **Gauge's `XamlRenderer.cs`/`XamlLayer.cs`** — architecturally blocked: arbitrary multi-stop `ColorBlend` gradients (no interface equivalent), arbitrary affine transforms including scale/shear (only rotate/translate are covered), and its geometry-parsing methods run with no live `GaugeGraphics`/`ResourceFactory` in scope at all.
- **Gauge's `HotRegionList.SetHotRegion`/`AddHotRegion` and `GaugeGraphics.DrawRadialSelection`** — systemic, concrete-only GDI+ hit-testing infrastructure used by every gauge element; no interface-typed overload exists anywhere. Bridged via a `UnwrapPath(IGraphicsPath):GraphicsPath` helper rather than converted; a distinct future milestone.
- **Gauge's `BufferBitmap`** — no `IRenderSurface`-equivalent abstraction yet (the Gauge analogue of Chart's own earlier `IRenderSurface`/`GdiRenderSurface` work), blocking `GaugeCore.Paint`/`PrintPaint`/`SaveTo`/`GetGraphics` and any second Gauge backend.
- **Gauge Skia backend — never started, low priority, not scheduled.** Gauge's GDI+→interface abstraction is complete (all resource types interface-typed, Gdi adapter pixel-verified), but no second backend was ever in scope for that effort — building one is new work, not a continuation. Expected shape, mirroring Chart's own E1/E2/F: a `Rendering/Skia/` adapter set mirroring Gauge's existing `Rendering/Gdi/`, a `GaugeCore.Paint`/`SaveTo` split analogous to Chart's `IRenderSurface` (which requires first solving the `BufferBitmap` gap directly above — deliberately left alone until a second backend actually exists, to avoid ceremony with no caller benefiting from it yet), and platform-selection wiring into `GaugeMapper.GetImage` analogous to Chart's `ChartRenderingBackendFactory`.
- **`ChartGraphics.cs`'s one remaining concrete allocation** — `GetTextureBrushResource`'s `Bitmap`/`Graphics.FromImage` compositing step, used only for `Metafile`-sourced images with a transparent color key. Deliberately concrete and permanent: `ImageLoader`'s own image-loading pipeline is GDI+-only by design, so this has nothing to abstract against. Every other concrete allocation in this file was either already covered by an interface-typed sibling or was found to be dead code once its real callers were traced (removed 2026-07-26) — don't expect a leftover conversion task here.

### Resolved gaps worth remembering (so they aren't rediscovered as "unsolved")

- **Chart Title font on non-Windows (fixed 2026-10-20, found on a real Linux server, not WSL).** Any RDL chart with a title vanished from PDF/Word: `Title.CalcTitlePosition`/`Paint` read `Title.Font`, whose getter lazily constructs a GDI+ `Font` (`DllNotFoundException: gdiplus.dll`). The earlier default-Font chase covered Legend/Axis only, and its WSL scenes had no title. Fix mirrors `Legend.GetBaseFontResource`: `Title.GetFontResource` ([Title.cs](../Microsoft.ReportViewer.DataVisualization/Microsoft.Reporting.Chart.WebForms/Title.cs)) never touches the `Font` property, and `ChartMapper.RenderTitleFont` hands the RDL family/size/style to `Title.SetFontDescriptor` (via `MapperBase.GetFontDescriptor`) when `GetFont` returns null, so the report's title font is kept. Other model classes whose `Font` getter is lazy (StripLine title, data-point labels, Annotation, LegendCellColumn...) may still hit the same wall if a report uses them — same fix shape applies.
- **Chart text ~3x too small in PDF/Word on non-Windows (fixed 2026-10-20).** PDF/Word ask for the chart image at a higher DPI than 96; GDI+ draws point-sized fonts at the bitmap's resolution (`Bitmap.SetResolution`), but `SkiaChartFont` converted points to pixels at a fixed 96 DPI, so titles/legends shrank by `dpi/96`. `SkiaChartGraphics` now draws/measures through `SkiaChartFont.GetNativeFont(dpi)`, using the DPI captured in `BindSurface`. `SkiaGraphicsPath.AddString` (Frame-style text only) still uses the 96-DPI font. Scenes rendered at 96 DPI (the visual baselines, the IMAGE renderer at default DPI) are unaffected — which is why WSL verification missed it.
- **Failed charts disappeared silently instead of showing an error image.** `DynamicImageInstance.CreateExceptionImage` drew the error box with GDI+, which itself failed on non-Windows and returned null, so PDF/Word just skipped the chart. It now draws with SkiaSharp there ([DynamicImageInstance.cs](../Microsoft.ReportViewer.Common/Microsoft.ReportingServices.OnDemandReportRendering/DynamicImageInstance.cs)). Diagnostic gotcha: `RSException.ToString()` strips stack traces for local reports, so walk `InnerException` and print each `StackTrace` explicitly when chasing such errors.

- **`GraphicsPath.Widen(Pen)`** (stroke-to-fill geometry) — has a real Skia equivalent via `SKPaint.GetFillPath` (Skia's own stroke-to-fill primitive), not a hand-rolled algorithm.
- **`SkiaGraphicsPath.AddArc`/`AddLine` must continue the current contour, not start a new one.** GDI+'s `GraphicsPath.AddArc`/`AddLine` continue the currently-open figure (connecting to the last point) when one is open; `SKPath.AddArc`/naive `MoveTo`+`LineTo` always start a fresh contour instead. Both bugs shipped silently (no exception, no visible break in most scenes) and were only caught by eyeballing a rendered PNG against its GDI+ baseline: `AddLine`'s version fragmented a multi-segment polyline into disconnected zero-area segments (`RangeChartWithGradient`'s whole-series gradient fill); `AddArc`'s version produced a self-intersecting "bowtie" where a doughnut/pie boundary is built from one continuous line+arc chain (`ChartGraphics3D.FillDoughnutSlice`'s inner hole). Fix for both: use `SKPath.ArcTo(rect, startAngle, sweepAngle, forceMoveTo: false)`/an explicit open-contour flag instead of `AddArc`/`MoveTo`+`LineTo` — `SkiaGraphicsPath.AddPie` already used the correct continue-or-start primitive. If a future scene shows a self-intersecting fill or a fragmented stroke with no thrown exception, suspect this class of bug first.
- **`SkiaGraphicsPath.PathTypes` must read `SKPath` via `CreateRawIterator()`, not `CreateIterator()`.** The "cooked" iterator (`CreateIterator`) synthesizes an extra closing line segment with no matching `PathPoints` entry, which breaks 1:1 alignment with GDI+'s `PathPointType` byte array (consumed directly by `HotRegionsList.AddHotRegion`'s `new GraphicsPath(points, types)` reconstruction). The raw iterator doesn't add that synthetic segment and maps cleanly.
- **`ImageAttributes`/`ColorMatrix` hue-recolor, shadow-alpha, and plain-transparency scaling** — all three recurring shapes are covered by a single `IImageDrawOptions.SetChannelScale(r, g, b, a)` method (a diagonal-only `ColorMatrix`, not a full matrix). A structurally identical, still-unconverted site exists in Chart's `ChartGraphics.cs` (~line 418), confirming the gap and its fix are shared across engines.
- **Brush rotation/translation transforms** (`LinearGradientBrush.Transform`, `PathGradientBrush.RotateTransform`/`TranslateTransform`) — covered by `SetRotationTransform`/`RotateTransform`/`TranslateTransform` on `ILinearGradientBrush`/`IPathGradientBrush`, deliberately as literal 1:1 ports of specific GDI+ call sequences rather than a generalized settable transform (to avoid unverified matrix-composition-order risk).
- **Gauge's `ScaleBase.DrawTickMark` wholesale `LinearGradientBrush.Transform = matrix` assignment** — `ILinearGradientBrush` deliberately has no generalized transform setter, but both real call sites always build `matrix` as a pure single rotation about one point, so it decomposes exactly (not an approximation) back to `SetRotationTransform(angle, center)` via `ScaleBase.DecomposeRotation`.
- **A "conclusion" from an earlier scoping pass is not evidence — always re-derive it from the current code before trusting it.** Gauge's `XamlRenderer.cs`/`XamlLayer.cs` were labeled "architecturally blocked" by one pass, then found on re-investigation to need only the same static-utility-threading pattern already solved elsewhere (`DigitalSegment.cs`) plus one new generalized brush-transform method — not a real blocker at all. Same category of mistake as Chart's D3/D3-real distinction above: a scoping label can outlive the reasoning that produced it, so re-check the reasoning, not just the label, before extending or accepting it.

## IMAGE renderer: `ImageWriter`/`Graphics.cs`/`MetafileGraphics.cs`

**Status: cross-platform, including Chart/Gauge/Map embedding (2026-07-31).** See `tasks/image-renderer-cross-platform.md` for the full scope and phasing; this section states current behavior.

`Graphics.cs` (the raster path behind BMP/GIF/JPEG/PNG/TIFF — EMF/EMF+ go through the separate `MetafileGraphics.NewPage`, see below) originally built its per-page bitmap via raw Win32 interop (`GetDC`→`CreateCompatibleDC`→`CreateDIBSection`→`SelectObject`→`Graphics.FromHdc`), then (once that was fixed) via a plain `new Bitmap(...)` — both of which hit GDI+, which cannot construct anything at all on Linux (the Phase 0 spike finding above). `Graphics.cs`, `ImageWriter.cs`'s draw overrides, and image decode (`PortableImage.cs`, wrapping the same `IImageProvider` abstraction Excel uses) were all reworked to branch on `OperatingSystem.IsWindows()` — the Windows branch is byte-for-byte the original GDI+ code; the non-Windows branch draws onto an `SKBitmap`/`SKCanvas` instead. **Verified for real, not just build-verified:** a text-free report (bordered/filled rectangle + dashed line) renders correctly end-to-end on Linux, visually confirmed by inspecting the actual output PNG.

**Narrower than full parity, and one gap still open:**
- SkiaSharp's `SKImage.Encode` only actually supports JPEG/PNG (BMP/GIF return null data) — those two, plus TIFF/EMF, stay Windows-only, throwing a clear exception rather than crashing.
- **Text now renders on non-Windows for IMAGE format (2026-07-28)** — `ImageWriter` overrides `DrawWrappedText`/`DrawWrappedRichText`, reusing `PDFWriter`'s `ShapedFontCache`/`ShapedTextWrapper` infrastructure for wrapping and a new `Graphics.DrawText` (SkiaSharp) for drawing. Visually verified under WSL: single-style and multi-run/multi-color/center-aligned rich text both wrap and position correctly.
- **Chart/Gauge/Map content now reaches the page on Linux for IMAGE format (fixed 2026-07-31).** The original symptom (`Renderer.ProcessDynamicImage` never getting real `DynamicImageContent` bytes, so `Writer.DrawDynamicImage` was never called) turned out to be a silently-swallowed exception in `DynamicImageInstance.GetImage`, not a missing code path. Root-caused and fixed via a 6-round WSL-trace-and-fix chase spanning `MapperBase.FontCache`, `Legend.AutoFitText`, `PieChart.CreateMapAreaPath`, `MapAreasCollection.Insert`, `DataPointAttributes`, and finally this renderer's own `ImageWriter.GetScreenDpi` (a raw Win32 HDC/`GetDeviceCaps` query, now gated behind `OperatingSystem.IsWindows()` with a 96/96 DPI default). WSL-verified with a real rendered Sunburst chart (nested rings, per-node labels, a Legend), 2.928% pixel-different from the Windows baseline (benign anti-aliasing variance). Full chase narrative in `tasks/chart-default-font-cross-platform.md`'s "Chase complete" section.

See `tasks/image-renderer-cross-platform.md`'s Phase 1/2/3 breakdown for what's done and what's left.

**EMF/EMF+ has no portable equivalent at all** — `MetafileGraphics.NewPage` calls `Graphics.GetHdc()` then constructs a real Windows `Metafile`, the same class of wall as Chart's `SaveIntoMetafile` (below). Permanent, Windows-only; guard rather than port.

## PDF (RDL engine): `PDFRenderer` → `Renderer` → `PDFWriter`

This is the real RDL PDF rendering path (`LocalReport.Render("PDF")`), distinct from the small standalone `LinuxPdfRenderer`/PdfSharpCore renderer in the row above. **Status: cross-platform rendering is complete.** `PDFWriter`'s own dependencies (embedded-image decode via `IImageProvider.DecodeToBgra32`, `PdfFontStyle` instead of `System.Drawing.FontStyle`, lazy `GraphicsBase`/`Renderer.ImageResources` construction) need no GDI+ at all. The reasoning behind each design choice below lives in `docs/decisions.md`; this section just states current behavior.

**Text rendering has two paths, selected by `PDFFont.EmbedFonts`:**
- **`FontEmbedding.Subset` (the default):** `PDFWriter` draws through a real, embedded, SkiaSharp-backed composite font (`GetOrCreateEmbeddedFont`/`WriteCompositeText`) — `CIDFontType2`/`FontFile2` for TrueType-outline fonts, `CIDFontType0`/`FontFile3`/`/Subtype /OpenType` for CFF-flavored ones (declared independently of outline format, a real PDF-spec distinction, not cosmetic). Supports full Unicode (not just WinAnsi), bidi/RTL run reordering (`BidiRunReorderer`), an OS/2 `fsType` embedding-rights check (`SkiaFontEmbeddingRights`), and glyph subsetting that never renumbers glyph ids (`TrueTypeGlyphSubsetter`/`CffGlyphSubsetter`, covering TrueType, non-CID and CID-keyed CFF, and TrueType Collection faces via `SfntBinaryUtils.TryExtractTtcFace`). A missing-glyph retry (`FontCache.GetFallbackFontCrossPlatform`, via `SKFontManager.MatchCharacter`) covers fonts that don't fully cover the requested script.
- **`FontEmbedding.None` (explicit opt-out only):** falls back to PDF's standard 14 fonts (Helvetica/Times/Courier), WinAnsi-only, with an approximate-but-real word-wrap driven by actually-shaped glyph widths, center/right alignment, and underline/strikethrough/overline decorations. An unrecognized font family is classified to the closest base-14 family by common serif/monospace name substrings (`ClassifyFallbackBase14Family`) rather than always defaulting to Helvetica.

**The shared RichText/Uniscribe production pipeline** (`FontCache`/`CachedFont`/`TextRun`/`LineBreaker`/`TextBox`/`Paragraph` — also used by the Windows-only `ImageWriter` extension, the WinForms on-screen viewer, and the `HPBProcessing`/`SPBProcessing` pagination engines) has real cross-platform branches for itemization (`UnicodeTextItemizer` — coarse Unicode-range script/direction classification, not a Uniscribe script-table port), line-breaking (`UnicodeLineBreakAnalyzer` — a hand-rolled, simplified approximation of UAX #14's pair-based algorithm, not certified-conformant), shaping (`HarfBuzzTextShaper` via `SkiaSharp.HarfBuzz.SKShaper`), and font metrics (`SkiaCachedFont`). PDF's `Renderer.ProcessSimpleTextBox`/`ProcessRichTextBox` route through this real pipeline rather than a simplified bypass, and pagination-phase text-box height measurement (`LineBreaker.FlowVerticalCrossPlatform`/`TextBox.MeasureFullHeightCrossPlatform`) is cross-platform too.

**Known remaining limitations, all narrow:** the WinForms on-screen viewer (`RichTextRenderer.cs`/`RenderingTextBox.cs`) itself remains Windows-only (shared infrastructure, not PDF-scoped); TrueType Collections bundling a CID-keyed CFF face (a rare combination) fall back to whole-file embedding; `UnicodeLineBreakAnalyzer` has no locale tailoring (kinsoku shori) or Unicode `LineBreak.txt` table.

**Resolved gap worth remembering (found only by actually running `LocalReport.Render("PDF")` under WSL, 2026-07-27):** `Renderer.ProcessSimpleTextBox`/`ProcessRichTextBox` correctly branch fresh `TextRun`s to `ShapeAndPlaceCrossPlatform` on non-Windows, but pagination's two-pass measure-then-render flow doesn't always construct fresh `TextRun`s — when a paragraph was already itemized once, the render pass reconstructs `TextRun` via the `TextRun(string, ITextRunProps, TexRunShapeData)` constructor from cached shape data instead. That cache (`TexRunShapeData.GlyphData`) only ever holds the Windows `ScriptShape` step's output; `ScriptPlace` still runs lazily against a real HDC via `LoadGlyphData`, which has no OS branch at all and always P/Invokes `Win32.ScriptPlace` (`usp10.dll`) — this is a genuinely Windows-only two-phase shape/place split with no non-Windows analogue (HarfBuzz's `SKShaper.Shape` always produces both together). Every unit-level cross-platform text test exercises only the fresh-`TextRun` path, so this was invisible without an actual end-to-end PDF render on a non-Windows OS. Fixed by leaving `m_cachedGlyphData` null on non-Windows in that constructor, so the first `GetWidth`/`GetGlyphData` call falls through to `ShapeAndPlace`'s existing `OperatingSystem.IsWindows()` branch and re-shapes for real via HarfBuzz instead of trying to "place" data that was never placed. If a future symptom looks like "PDF text rendering throws `DllNotFoundException` for `usp10.dll`/`User32.dll` on Linux/macOS despite the cross-platform shaping path existing," suspect this class of bug — a Windows-only intermediate cache being reused as if it were a complete, cross-platform-safe shape result.

## Guidance

When introducing a new renderer implementation, prefer:

- a small interface for the contract,
- a platform-specific implementation behind that contract,
- a factory or registration point for selection,
- and tests that verify the behavior rather than the visual output.
