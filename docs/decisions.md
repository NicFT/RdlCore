# Architecture decisions

## Decision: introduce thin render abstractions

The rendering layer now uses small interfaces for Excel and PDF output rather than embedding platform-specific logic directly in the call sites. This keeps the implementation modular and makes it easier to swap in additional implementations later.

## Decision: use a factory for renderer selection

Renderer selection is centralized in the factory rather than being repeated across the codebase. The factory provides a single place to decide which implementation should handle a given platform and format.

## Decision: use adapters for resource handling

The new resource adapter normalizes embedded-resource payloads before the rendering layer uses them. This reduces coupling to a specific resource representation such as a stream, string, or byte array.

## Why these choices

- They preserve backwards compatibility with the existing codebase.
- They minimize the amount of new infrastructure needed for the first cross-platform seam.
- They make it easier to extend the design as additional renderers are introduced.

## Decision: OxyPlot chart-library replacement — retracted (2026-07-13)

An earlier decision to replace the vendored `Microsoft.Reporting.Chart.WebForms` engine with OxyPlot 2.1.x was reviewed against the actual code and retracted. Reasons:
- The chart engine is not an external dependency — it's ~400 files of vendored source the repo owns, with an existing `IChartRenderingEngine` seam the original evaluation never considered.
- Cited performance/coverage numbers and supporting analysis documents backing the OxyPlot decision could not be found or reproduced.
- Replacing the engine would mean re-implementing the RDL chart model (40+ chart types, 3D, financial, radar, annotations, statistical formulas, palettes) onto a different library's model — a compatibility break, not a port.
- Gauges use a separate engine (`GaugeContainer`/`Microsoft.Reporting.Gauge.WebForms`) that a chart-library swap wouldn't have touched anyway.

**Replaced by:** re-targeting the existing `IChartRenderingEngine` seam to SkiaSharp via the Ports & Adapters design in `docs/rendering-abstractions.md`. OxyPlot (or any other library) remains an option only if a visual/pixel-parity break is acceptable — not as a validated drop-in.

## Decision: re-target the vendored Chart/Gauge engines to SkiaSharp, not replace them

A Phase 0 spike (2026-07-18) confirmed the plan: keep the vendored GDI+ engines, but make their resource types (`Pen`, `Brush`, `Font`, `GraphicsPath`, …) backend-agnostic so a SkiaSharp backend can be swapped in behind the existing rendering seam. The spike found that on .NET 10 under Linux, **every** bare `System.Drawing` object construction (`Font`, `Pen`, `SolidBrush`, `GraphicsPath`, `Bitmap`) throws `DllNotFoundException` even with `libgdiplus` installed — this rules out any "wrap and translate GDI+ descriptors" approach and confirms full type abstraction (not just a rendering-seam swap) is required before Linux/macOS chart rendering is possible at all. A hand-built Skia scene, written only against the abstracted port, rendered correctly and identically on both Windows and Linux, validating the design. See `docs/platform-support.md` for the current state of this migration.

## Decision: interfaces (not descriptor records) for every resource type, including pure-data ones

`Pen`, `Brush`, `Font`, and `StringFormat` are pure parameter bags and could have been modeled as `readonly record struct`s. Interfaces were chosen uniformly instead, for extensibility and one consistent factory pattern — while allowing `record`-shaped concrete implementations behind those interfaces where a resource really is pure data.

## Decision: per-method/per-caller conversion instead of per-type

The original migration plan sequenced work by GDI+ *type* (convert all `Pen` usage, then all `Brush` usage, etc.). In practice, real painter code bundles types together (a single `DrawStringRel` call touches `Font`+`Brush`+`StringFormat`; `DrawPath` touches `Pen`+`GraphicsPath`), so "finish type X" checkboxes were redefined to mean "the interface + adapter for X is complete," with actual call-site conversion done per-method/per-file (tracked as Milestone B2) using the dual-overload pattern described in `docs/rendering-abstractions.md`.

## Decision: keep old GDI+-typed overloads alongside new interface-typed ones (never a big-bang signature change)

`IChartRenderingEngine`/`IGaugeRenderingEngine` and `ChartGraphics`/`GaugeGraphics` keep their original GDI+-typed methods indefinitely while new interface-typed siblings are added next to them. This is what allows the migration to proceed in small, independently buildable/testable increments without ever breaking the build; removing the temporary concrete overloads is its own later milestone (Chart's "D3"), not assumed to happen automatically once callers migrate.

## Decision: share pure resource interfaces between the Chart and Gauge engines, but not the adapters or clip-region interface

When the Gauge engine's migration began, Chart's already-drafted resource interfaces (`IPen`, `IBrush` family, `IChartFont`, `ITextFormat`, `IGraphicsPath`, `IChartImage`, `IImageDrawOptions`) were relocated from a Chart-only namespace into the neutral `Microsoft.Reporting.Rendering` namespace and reused as-is, rather than duplicated or cross-referenced. `IClipRegion` could not make the same move — it depends on `IChartRenderingEngine` to reach a live `Graphics`, a genuine per-engine coupling — so Gauge got its own, separately-defined `IGaugeClipRegion`. Concrete adapters (`GdiPen`, `GdiBrush`, etc.) are likewise implemented separately per engine even when identical in shape, rather than shared instances.

## Decision: `ImageLoader`'s DPI-mismatch rescaling was dropped, not ported (Chart engine)

GDI+'s image-loading path auto-rescaled images when their embedded resolution (`Image.HorizontalResolution`/`VerticalResolution`) differed from the target `Graphics.DpiX`/`DpiY` — a print/high-DPI nuance. `SKBitmap` carries no resolution metadata, so porting this faithfully would require adding meaningless-on-Skia resolution properties plus a resize capability, just for an edge case ordinary web/screen chart images essentially never hit. Decision: assume a fixed 96 DPI baseline and drop the rescale path entirely. This is a real, accepted behavior change on Windows too — an image asset explicitly authored at a non-96 DPI now renders at native pixel size instead of being auto-rescaled — judged acceptable since it's narrow, cosmetic, and not exercised by this engine's real usage.

## Decision: approximate two GDI+ brush kinds with no direct Skia primitive, rather than hand-roll exact ports (Chart engine, 2026-07-23)

Two GDI+ brush kinds have no SkiaSharp equivalent primitive:
- **`PathGradientBrush`** — `SkiaPathGradientBrush` approximates it with `SKShader.CreateRadialGradient` centred on the source path's bounds. This is exact for the elliptical shadow/soft-edge/doughnut fills the engine's real callers actually build (`ChartGraphics.DrawPieSoftShadow`, `DrawMarkerAbs`'s soft circular-marker shadow, `DrawPieGradientEffects`'s `Concave`/`SoftEdge` styles), and only an approximation for a non-elliptical path or >1 surround colour — GDI+'s true per-boundary-point interpolation has no single-shader Skia equivalent.
- **`HatchBrush`** — GDI+'s hatch patterns are undocumented internal bitmaps with nothing to port against. `SkiaHatchPatterns.BuildTile(HatchStyle, foreColor, backColor)` generates a small tileable bitmap per style via deterministic pixel predicates (modular line/diagonal tests for the line-family styles, a coordinate-hash bucket for the `Percent*` density fills, combined predicates for the grid/checker/diamond/brick/wave families), tiled via `SKShader.CreateBitmap(..., Repeat, Repeat)`. Covers every current `HatchStyle` member plus a generic cross-hatch fallback for any future BCL addition.

Both are documented, honest visual approximations, not pixel-exact ports — accepted because GDI+'s exact algorithms are either undocumented (`HatchBrush`) or have no equivalent shader model (`PathGradientBrush`'s per-point interpolation), and the approximation is exact for every real call site this engine exercises.

## Decision: replace SixLabors.ImageSharp with SkiaSharp in the Excel image path (2026-07-28)

`CrossPlatformImageProvider`, `ImageFormatTypeHelper.DetectFromStream`, and `ImageInformation.CalculateMetrics` used ImageSharp (`Image.Identify`, `Image.Load<Bgra32>`, `SaveAsPng`) purely for format/size sniffing, BGRA32 decode, and PNG re-encode — all operations `SKCodec`/`SKBitmap` already cover, and SkiaSharp was already a mandatory dependency for chart/PDF text rendering. Removing ImageSharp drops a whole package family with no loss of function. The one gap: SkiaSharp has no embedded-resolution (DPI) metadata, so these call sites now assume a fixed 96 DPI baseline — the same accepted tradeoff already made for `ImageLoader`'s DPI-mismatch rescaling in the Chart engine (above). The visual-regression test projects' `ImageComparer` helpers were ported the same way (`SKBitmap.GetPixel`/`SetPixel` in place of ImageSharp's indexer) since they only pulled ImageSharp in for pixel-diffing PNGs.

**Pin capped at 3.1.x (2026-10-29):** `SixLabors.ImageSharp` 3.2.0+ and 4.x ship a `build/SixLabors.ImageSharp.targets` that fails the build with "No Six Labors license found" unless `SixLaborsLicenseKey`/`SixLaborsLicenseFile`/`sixlabors.lic` is supplied. The direct pin in `Microsoft.ReportViewer.Common.csproj` therefore stays on **3.1.12**, the last version without that gate. 3.1.12 is still inside the range of several GitHub advisories (GHSA-j3p4-wp97-rph4 and others, first patched in 3.2.0/4.1.2), so `dotnet restore` reports NU1902/NU1903. Accepted risk: ImageSharp code is not reached at runtime. Its only consumer is `PdfSharpCore`'s `XImage` loading, and `Renderers/LinuxPdfRenderer.cs` uses only `XFont`/`DrawString`. The real fix is removing `PdfSharpCore`, which would drop ImageSharp entirely.

**SkiaSharp 4.x API changes (2026-10-29):** the 4.x reference assembly removed `SKFilterQuality` and `SKRunBuffer.GetGlyphSpan()`/`SKPositionedRunBuffer.GetPositionSpan()`. Replacements: `SKFilterQuality.High` → `new SKSamplingOptions(SKCubicResampler.Mitchell)` (the same mapping SkiaSharp 3 applied internally), and the span getters → the `Glyphs`/`Positions` properties.

**ILRepack 2.0.48 drops the strong name (2026-10-29):** unlike 2.0.46, the 2.0.48 merge engine writes `bin/Release/.../Microsoft.ReportViewer.NETCore.dll` without a public key unless the `ILRepack` task gets `KeyFile`. Without the key, `Microsoft.ReportViewer.Common`'s `InternalsVisibleTo("Microsoft.ReportViewer.NETCore, PublicKey=…")` no longer matches, and every `LocalReport` construction throws `MethodAccessException` (`StandalonePreviewStore..ctor`). `Microsoft.ReportViewer.NETCore/ILRepack.targets` now passes `KeyFile="$(MSBuildProjectDirectory)\$(AssemblyOriginatorKeyFile)"` explicitly.

## Decision: Map engine migration deferred, LOW priority, scheduled after PDF (2026-07-22)

The Map engine (`Microsoft.Reporting.Map.WebForms`) was found during Chart's D3 scoping to be a third, separate, parallel GDI+-coupled rendering engine (347 files, ~22,400 lines) — not shared with Chart or Gauge — that a full cross-platform migration would need to repeat the entire Ports & Adapters treatment for a third time. It's a real, wired-in RDL feature (`MapMapper.cs` + ~20 sibling mapper classes translate report-definition `<Map>` XML into it, the same pattern `ChartMapper`/`GaugeMapper` use), not dead code, but its built-in tile-service integration (`Microsoft.Reporting.Map.WebForms.BingMaps`) depends on Bing Maps, which Microsoft has end-of-lifed for RDL/RDLC consumers — preliminary research indicates neither the Bing Maps Free nor Enterprise tier is supported for this use case any longer.

Decision: deprioritize the Map engine to **LOW**, ordered after PDF Phase 1 in `TODO.md`'s priority table — not because the migration mechanics differ from Chart/Gauge, but because (a) its main built-in value-add (Bing tile layers) is already broken independent of any cross-platform work, and (b) PDF's own blocker is architecturally deeper (full Metafile/EMF replacement) and was already judged higher-priority than a third from-scratch engine migration. If Map is revisited, the tile-service question needs its own decision first — options include a Google Maps adapter (commercial API, usage-based billing, ToS review needed) or an OpenStreetMap adapter (tile-server-based, no API key, but usage-policy/self-hosting considerations for production volume) — before any GDI+→interface migration work on Map itself would be worth starting.

**Tile-service default (2026-07-28):** picked **OpenStreetMap** as the default adapter target, so the migration is unblocked for whoever picks it up next. Reasoning: no API key or commercial billing relationship to set up (Google Maps requires both), and RdlCore already has no other paid-API dependency anywhere in the rendering stack — introducing one for Map alone would be a new category of operational cost for users of this library. The tradeoff being accepted: OSM's tile-usage policy caps unattributed/high-volume production use, so a real deployment may eventually need self-hosted tiles — a hosting concern for whoever deploys it, not a blocker for the adapter code itself. This is a placeholder decision the repo owner can override; it exists only to unblock scoping/implementation, not to foreclose reconsidering it.

**Migration scoped, not started (2026-07-28):** a survey (see `tasks/map-engine-cross-platform.md`) found the "347 files" figure above overstates the real conversion surface — only ~24 files actually contain direct GDI+ drawing calls (smaller than Chart's own 73-file painter surface), the rest being data-model/converter/collection classes. Map already has its own GDI+-concrete rendering chokepoint (`IMapRenderingEngine`/`MapGraphics`), structurally identical to what `IChartRenderingEngine`/`IGaugeRenderingEngine` looked like before their own migrations — meaning the Ports & Adapters shape is directly reusable, and the neutral `Microsoft.Reporting.Rendering` interfaces (`IPen`/`IBrush`/`IChartFont`/`IGraphicsPath`/`IChartImage`) should be directly reusable too, no Map-specific resource kinds found. One real structural difference from Chart: Map's raw `Bitmap`/`Metafile`/`GetHdc` construction happens directly in `MapMapper.cs`, one layer above the rendering engine, so the render-surface abstraction needs to reach one layer higher than Chart's did. Still LOW priority, still not started — this is scoping only.

## Clarification: "D3 permanently blocked" is about removing concrete overloads, not about 3D rendering on Skia (2026-07-24)

Chart's D3 milestone status ("permanently blocked by design") is scoped narrowly to one specific goal: removing the temporary concrete `GraphicsPath`-returning overloads from `LineChart`/`AreaChart`/`RangeChart`/`StepLineChart`/`KagiChart`/`StackedAreaChart`'s shared `Draw3DSurface`/`Draw3DPolygon` virtual method family, which genuinely can't happen piecemeal because every override of one virtual method must share its signature, and `AreaChart`'s override is entangled with concrete-only `ClipTopPoints`/`ClipBottomPoints` helpers.

This does **not** mean 3D chart rendering is impossible on a Skia backend. `ChartGraphics3D` performs all "3D" rendering as ordinary perspective-projected 2D drawing (paths, polygons, gradients) dispatched through `IChartRenderingEngine` — there is no actual 3D/GPU rendering anywhere in this engine. Most of that surface already has interface-typed siblings from D3's own completed work (`Draw3DSurfaceResource`, `Draw3DPolygonResource`, `Fill3DRectangleResource`/`Fill3DRectangleAsCylinderResource`, `DrawMarker3DResource`). The only remaining piece — converting the `LineChart`/`AreaChart`-family virtual dispatch chain itself — was a bounded, ordinary type-conversion task, not a capability gap, and was completed as Milestone "D3-real" (2026-07-26): every 3D chart scene now renders correctly through the Skia backend. This clarification is kept here specifically so "D3 permanently blocked" is never misread as "3D is impossible on Skia" in a future session.

## Clarification: `ChartMapper.GetImage`'s real path vs. `ChartImage.GetImage`'s permanent wall (2026-07-24)

`ChartImage.GetImage(float) : Bitmap` has a hard external contract (a concrete `System.Drawing.Bitmap` return type) that can never be satisfied on Linux, per the Phase 0 spike finding that `Bitmap` construction itself throws there. This is a real, permanent gap — but it does not block Chart rendering in general, because it isn't the real production entry point. The actual RDL rendering path is `ChartMapper.GetImage(ImageType)` → `Chart.Save(Stream, ChartImageFormat)` → `ChartImage.SaveImage(...)`, which never returns a `Bitmap` and already routes through `IRenderSurface.Encode`. Chart's Milestone F tracks wiring platform selection into that reachable path; nothing tracks (or should track) trying to fix `GetImage` itself.

## Clarification: PDF path vs. Image-renderer path — the old "Metafile blocker" doesn't apply to PDF (2026-07-24)

The original PDF analysis docs (`tasks/pdf-render-callstack-analysis.md`, `tasks/pdf-quick-reference.md` — since removed, their durable conclusions folded into this file and `docs/platform-support.md`; written 2026-07-13) concluded PDF rendering needed a full GDI+/Metafile-to-SkiaSharp graphics-stack replacement, citing `MetafileGraphics.cs`/`Graphics.cs`/`GraphicsBase.cs`. Re-reading the actual call chain (2026-07-24) found this conflated two separate rendering extensions that happen to share source files: `PDFRenderer`→`Renderer`→`PDFWriter` writes PDF content-stream operators directly (`PDFWriter.DrawLine` etc. append literal PDF path/stroke operators to a `StringBuilder`) and never calls into `Metafile`, `System.Drawing.Graphics` drawing methods, or `Pen`/`Brush`/`GraphicsPath`. Those GDI+ types are used only by `ImageWriter`, the separate BMP/GIF/JPEG/PNG/TIFF/EMF rendering extension, which is not reachable from `LocalReport.Render("PDF")`.

PDF's real remaining dependencies are much narrower: two `Bitmap` decode call sites (same shape as Excel's `IImageProvider` pattern), a trivial `FontStyle` enum, four bounded Win32 HDC font-metrics call sites (map to `SKFont` equivalents, plus a font-table-parsing need for embedding-rights checks), and `Microsoft.ReportingServices.Rendering.RichText`'s Uniscribe-based complex-script shaping/line-breaking (`LineBreaker.cs`/`TextBox.cs`, ~1,375 lines calling `usp10.dll`) — a genuinely large, open item needing a HarfBuzzSharp/ICU-based redesign, since no shaping/bidi engine exists in this repo to reuse or extend. See `tasks/pdf-render-callstack-analysis.md`'s phase plan (P0-P4) for the corrected breakdown. This is the same "a blocked/scoped label can outlive its reasoning" pattern noted for Gauge's `XamlRenderer.cs` and Chart's D3 — worth re-deriving before trusting an old analysis doc's conclusion, not just this doc's.

## Correction: P4 ("Uniscribe complex-script shaping") understated the real scope — it's PDF's universal text-shaping mechanism, not an RTL/complex-script edge case (2026-07-26)

Implementing P1-P3 (image decode via `IImageProvider`, `PdfFontStyle` enum, `GraphicsBase` lazy construction — all done, see `tasks/pdf-render-callstack-analysis.md`) required tracing P4 for real rather than taking the prior "complex-script shaping, ~1,375 lines" framing at face value. Two findings change the picture materially:

1. **`Win32.ScriptShape`/`ScriptPlace` (Uniscribe) are called unconditionally for every text run, regardless of script.** `TextRun.ShapeAndPlace` (`Microsoft.ReportingServices.Rendering.RichText/TextRun.cs:356-451`) has no simple/Latin fast path — `TextRun.GetCharset()` only picks a charset/font-fallback hint, it never skips shaping. This means Uniscribe isn't a complex-script-only dependency to work around; it's the sole text-shaping backend for *all* text this engine renders, including plain English/Western reports. A cross-platform replacement (HarfBuzzSharp + a bidi/line-break algorithm, per the existing P4 recommendation) is required for *any* text to render on Linux, not just RTL/CJK/Indic content.
2. **The text-shaping pipeline constructs live GDI+ `Font` objects and real Win32 `HFONT`s for every run, upstream of Uniscribe.** `FontCache.CreateFont` (`RichText/FontCache.cs:174-195`) calls `CreateGdiPlusFont` (`new Font(...)`, `RichText/FontCache.cs:309-409`) and `Win32.CreateFont` (a real `CreateFontW` P/Invoke, `RichText/FontCache.cs:221`) for every distinct font/run combination. `new Font(...)` construction is blocked on Linux independent of Uniscribe (the Phase 0 spike's "GDI+ can't construct any System.Drawing object on Linux" finding, `docs/platform-support.md`) — so even a hypothetical Uniscribe replacement wouldn't be sufficient on its own; `CachedFont`/`FontCache`'s GDI+ Font construction is an equally hard, separate wall in the same pipeline.

**Blast radius is wider than PDF.** `LineBreaker.Flow`/`RichText.TextBox.Render` are called from `Renderer.cs` (used by both `PDFWriter` and the Windows-only `ImageWriter`/EMF/TIFF path), `RichTextRenderer.cs`/`Microsoft.Reporting.WinForms/RenderingTextBox.cs` (the WinForms on-screen viewer), and `Microsoft.ReportingServices.Rendering.HPBProcessing`/`SPBProcessing`'s `PageContext.cs` (the shared pagination/page-break engine feeding all renderers, not just PDF). Fixing this properly benefits PDF, the on-screen viewer, and pagination correctness together — but it also means PDF cannot get *cheaper* text support by working around some renderer-specific shortcut; there isn't one to find, because the dependency is shared infrastructure.

**Also found and fixed (2026-07-26), unconditional at a much earlier point than the 4 HDC call sites:** `Renderer`'s static constructor (`ImageRenderer/Renderer.cs`) built `System.Drawing.Bitmap` objects (`ImageResources`) unconditionally at type-load time — meaning merely loading the `Renderer` type (which every PDF render does) crashed on Linux before reaching any of P1-P4. Made lazy (`Renderer.ImageResources` is now a lazily-initialized property). `GraphicsBase`'s constructor had the identical eager-construction shape (`new Bitmap(2,2)` + `Graphics.FromImage` on every `WriterBase.BeginReport`, i.e. every PDF render) and got the same fix — `GraphicsBase`'s `Bitmap`/`Graphics` pair is now built lazily on first real HDC/text-metrics use (`GraphicsBase.cs`'s `EnsureGraphics()`), so a text-free PDF (lines/rectangles/images only) no longer crashes at construction. Text-containing reports still hit the `FontCache`/Uniscribe wall described above.

**Conclusion:** P1-P3 are genuinely done and real progress (verified: `dotnet build` 0 errors, full test suite passing, a new end-to-end `SunburstChartWithCategoryHierarchy_RendersToPdf` test exercising the real `PDFRenderer`→`Renderer`→`PDFWriter` path). P4 is not a bounded "spike it and see" item as previously scoped — it is the actual, singular blocker standing between this codebase and any text rendering on Linux across PDF, Image, WinForms-viewer, and pagination. Treat it as its own multi-session migration on the scale of Chart/Gauge's GDI+ abstraction (or larger, since it requires new shaping/line-breaking logic, not just resource-type ports) — see `tasks/pdf-text-shaping-abstraction.md` for the scoped starting point.

## Decision: ship a base-14-font MVP for simple PDF text boxes instead of building the full Skia/HarfBuzzSharp shaping port first (2026-07-26)

The plan above (and `tasks/pdf-text-shaping-abstraction.md`'s original phased plan) assumed the only way to get real text into a PDF on Linux was a full replacement of RichText's shaping pipeline — a large, multi-session undertaking. Tracing PDFWriter's own font-metrics call sites (`ProcessDrawStringFont`/`WriteFont`/`WriteEmbeddedFont`/`ProcessFontForFontEmbedding`, previously scoped as "P3, bounded, independent of P4") down to their actual inputs found that scoping was itself wrong: those call sites all read from a live `RichText.CachedFont` that only exists because the RichText pipeline already ran successfully — they're unreachable on Linux regardless of how portable `PDFWriter`'s own code is. P3 was never independently completable; it was gated by P4 the whole time.

That finding pointed at a much smaller unlock: PDF's standard 14 fonts (Helvetica/Times/Courier families) need no embedded font data or `/Widths` array at all — real PDF readers already know their metrics, and `PDFWriter`'s existing `WriteFont` already has an `InternalFont` fast path proving this (it emits only `/BaseFont /Helvetica /Encoding /WinAnsiEncoding` for these, nothing else). Combined with the observation that `PDFWriter` never emits explicit per-glyph positions for non-embedded fonts (it relies on the PDF reader's own font metrics to lay out `Tj` text), a whole-new, small, dependency-free code path became possible: resolve any requested font family to the nearest base-14 font, word-wrap using an approximate (not exact) character-width table, and emit `BT/Tf/Td/Tj/ET` directly — bypassing `RichText.LineBreaker`/`TextBox`/`FontCache`/`CachedFont`/`TextRun` (and therefore Uniscribe and GDI+ `Font` construction) entirely for simple (single-style) text boxes.

This shipped as a real, verified feature (2026-07-26): `CrossPlatformTextLayout.cs` (`ApproximateTextMetrics`/`SimpleTextWrapper`), `WriterBase.DrawWrappedText`/`PDFWriter.GetOrCreateBase14Font`/`DrawWrappedText`, and a platform branch in `Renderer.ProcessSimpleTextBox`. Verified end-to-end by temporarily forcing the branch on this Windows dev machine and rendering a real PDF (correct word-wrap, correct position, correct font) — see `tasks/pdf-text-shaping-abstraction.md`'s "MVP" section for the full trace and the honestly-scoped gaps (no rich/multi-run text, font family not honored beyond the base-14 map, approximate wrap widths, left-align only).

This does not replace the SkiaSharp/HarfBuzzSharp shaping-port plan — that's still the path to full fidelity (real embedded fonts, exact metrics, arbitrary Unicode, RTL/complex scripts). It changes what's blocking on what: "text boxes render on Linux" no longer requires that larger port to ship first. This is the same category of finding as the Chart/Gauge "a scoping label can outlive the reasoning that produced it" lesson (`docs/platform-support.md`) — re-deriving P3's actual reachability, rather than trusting its prior "bounded and independent" label, is what surfaced the shortcut.

The same-day extension to rich (multi-run/multi-paragraph) text boxes (`Renderer.ProcessRichTextBox`/`WriterBase.DrawWrappedRichText`) confirmed the approach generalizes: `StyledTextWrapper.WrapParagraph` word-wraps across run boundaries and merges adjacent same-style fragments, while drawing still relies on the PDF reader's own post-`Tj` position advance rather than computed per-fragment coordinates - so mixing fonts/styles within a line needed no new positioning logic, only per-fragment `Tf`/color emission. Verified the same way (temporarily forced locally, rendered a bold-prefix/normal-suffix run pair plus a separately-styled italic paragraph, confirmed correct, reverted).

Center/right text alignment, originally cut from the MVP's scope as "riskier than shipping left-align-only," was added the same day once the approach was better understood: each wrapped line's start-x (not its internal glyph positions, which the PDF reader still lays out itself) is the only thing alignment needs to change, computed from the same approximate width table already used for word-wrap. Line-to-line movement switched from `TL`/`T*` to an explicit relative `Td` per line to allow different lines their own start-x. Verified the same way (forced locally, rendered a centered title and a right-aligned line, both visually correct).

Underline/strikethrough were added the same day, closing out the font-decoration work for now (font families beyond base-14 are explicitly deferred per user direction, until after PDF rendering is otherwise end-to-end). The one wrinkle: PDF text objects (`BT`/`ET`) can't contain path-painting operators, so decoration rectangles are emitted as a separate content-stream fragment right after each text block, using the same `WriteColor`+`re f` pattern the existing `FillRectangle` method already uses elsewhere in `PDFWriter`. For rich text, each styled fragment's rectangle position is tracked by accumulating the same approximate character-width estimates already used for word-wrap - an approximation, not exact, but consistent with the rest of this MVP's stated tradeoffs. Verified the same way as prior increments (forced locally, rendered whole-line underline, whole-line strikethrough, and a mixed-decoration rich-text paragraph, all visually correct, reverted).

## Decision: use `SkiaSharp.HarfBuzz.SKShaper`, not a hand-rolled `HarfBuzzSharp.Face`/`Font`, for the P4 shaping prototype (2026-07-26)

The P4 shaping prototype (`HarfBuzzTextShaper.cs`) originally built its own `HarfBuzzSharp.Blob`/`Face`/`Font` from a raw font-stream blob (via `SKTypeface.OpenStream`), matching the Phase 1 spike's approach. This has a native lifetime bug: it crashed the test host with an access violation (`0xC0000005` in `hb_shape_full`) once enough shape calls had accumulated across a test run — never within one isolated test, only cumulatively, and independent of whether the `Face`/`Font` was rebuilt per call or cached once per `SkiaCachedFont` instance. See `docs/troubleshooting.md` for the crash signature.

Fix: use `SkiaSharp.HarfBuzz.SKShaper` — the official HarfBuzzSharp+SkiaSharp integration package, already proven stable by this repo's own `ShapedTextRasterizer` (`tests/RdlCore.LinuxRenderers.Tests`) — instead of hand-building the native objects. `SkiaCachedFont` now owns one `SKShaper` per instance; `HarfBuzzTextShaper` derives per-glyph advances from `SKShaper.Result.Points`'s cumulative pen positions rather than reproducing Uniscribe's separate advance+`GOFFSET` model (`GOFFSET` is now always zero — an honest simplification). Verified stable across repeated full-suite runs after the switch.

**Lesson for future native-interop prototyping in this repo:** when a proven high-level wrapper exists for a native library this repo already depends on, prefer it over hand-rolling the lower-level API, even for a throwaway prototype — the cost of a subtle native lifetime bug (intermittent, cumulative, hard to repro in isolation) is much higher than the cost of the extra abstraction layer. Composing several small prototypes together (here: itemizer + line-breaker + shaper into one pipeline) is also what surfaced this bug — none of the shaper's own isolated unit tests hit it, only the higher shape-call volume of the composed pipeline did. Test compositions, not just units, before trusting a prototype.

## Decision: wire the P4 shaping prototypes into the base-14 MVP for measurement only, not for drawing (2026-07-26)

With the P4 shaping/itemization/line-break prototypes composed and stable (`UnicodeParagraphShaper`, see the `SKShaper` entry above), the next question was what "production wiring" should mean given font embedding is still deferred. Two readings were possible: (a) build a full parallel cross-platform `LineBreaker`/`TextBox` replacement for true full-fidelity rich text, or (b) use the prototypes only to make the existing base-14 MVP's word-wrap and decoration-sizing decisions more accurate, without touching how glyphs are drawn. Chose (b): real embedded fonts are still out of scope, and (a) would mean building substantial new layout machinery whose value is capped by the same "still base-14, still approximate at the drawing layer" ceiling until embedding lands anyway.

`Microsoft.ReportingServices.Rendering.ImageRenderer/ShapedTextLayout.cs` replaced `CrossPlatformTextLayout.cs`'s `ApproximateTextMetrics`/`SimpleTextWrapper`/`StyledTextWrapper` (deleted as dead code once superseded) with `ShapedFontCache`/`ShapedTextMetrics`/`ShapedTextWrapper`/`ShapedStyledTextWrapper`, which measure real per-character glyph advances and soft-break opportunities via `UnicodeParagraphShaper` instead of a fixed character-class width table. `PDFWriter.DrawWrappedText`/`DrawWrappedRichText` now call these. Drawing is unchanged - still a base-14 font via plain-text `Tj`, still relying on the PDF reader's own metrics to position glyphs. This means word-wrap decisions now use one font's real shaped widths while the drawn glyphs use whatever base-14 font the reader substitutes - a real accuracy improvement (exact per-glyph widths of an actual resolved font, real soft-break rules, no mid-word splits) over the fixed approximation table, but not a correctness guarantee, since the two fonts can still differ.

This is a genuinely separate increment from the "full-fidelity RichText/Uniscribe replacement" described in `tasks/pdf-text-shaping-abstraction.md`'s phased plan - that plan's parallel `LineBreaker`/`TextBox`-equivalent, real font embedding, and the platform-selection seam inside `TextRun`/`FontCache` are all still unstarted. This entry exists so a future session doesn't conflate "the P4 prototypes are wired into PDFWriter" (true, for measurement) with "full-fidelity rich text now renders on Linux" (not true - still base-14 only).

## Decision: grant `InternalsVisibleTo` to a test project instead of continuing manual-only verification of the cross-platform PDF text path (2026-07-26)

Every increment above (`DrawWrappedText`/`DrawWrappedRichText`, alignment, decorations) had to be verified by *manually* forcing `Renderer`'s `!OperatingSystem.IsWindows()` branch on this Windows dev box, rendering a real PDF, and reverting - because `Renderer`/`PDFWriter` are `internal`, and `Microsoft.ReportViewer.Common`'s `AssemblyInfo.cs` only grants `InternalsVisibleTo` to `Microsoft.ReportViewer.NETCore`/`Microsoft.ReportViewer.WinForms`. No automated test could call the cross-platform methods directly or otherwise assert this branch runs at all, on any platform.

The earlier framing of this gap (see the now-superseded gap note in `tasks/pdf-text-shaping-abstraction.md`) treated closing it as requiring either a weakened platform check or "touching signing infrastructure," broad enough to warrant deferring without the user's sign-off. On revisiting: every test project in this solution — including `Microsoft.ReportViewer.Chart.Rdl.Tests` — is already signed with the *same* `RdlCore.snk` key as `Microsoft.ReportViewer.Common` (same `AssemblyOriginatorKeyFile` in both `.csproj` files). Granting that test assembly an `InternalsVisibleTo` entry, keyed to that same already-trusted public key, introduces no new key and no new trust boundary — it's the identical pattern already used for `NETCore`/`WinForms`, just extended to one more assembly built from the same signing material.

Once granted, `CrossPlatformPdfTextTests.cs` constructs a minimal `Renderer`/`PDFWriter`/`MemoryStream` directly and calls `DrawWrappedText`/`DrawWrappedRichText`, asserting on the emitted PDF content-stream operators (`Tj`, `re f`) — this exercises the real cross-platform code path on every test run and every platform, not just when someone remembers to force the branch by hand. This is a permanent, standing regression gate where there was none before, at the cost of one more assembly added to an internal API's already-existing allowlist.

## Decision: reverse the font-embedding deferral once bidi/RTL work proved base-14 was a dead end (2026-07-26, same day)

The plan for this increment was to extend `DrawWrappedText`/`DrawWrappedRichText` further using the P4 shaping prototypes — specifically, bidi/RTL reordering for Hebrew/Arabic text, per the "extend PDFWriter's path further" scope the user picked over "replace the real RichText pipeline." Implementing it (a `BidiTextReorderer` reversing consecutive RTL item runs, using `UnicodeTextItemizer`'s existing per-run `fRTL` flag) worked, but turned out to be dead code: base-14 fonts only support `/Encoding /WinAnsiEncoding` (cp1252) — zero Hebrew/Arabic/Cyrillic/Greek/CJK code points — and `PDFWriter.WriteText`'s literal-Tj branch already silently drops/mangles anything outside that table. Reordering RTL runs correctly doesn't help when the glyphs can't be drawn on that path at all, regardless of order. The reordering code was reverted rather than left in as unreachable-in-practice complexity (matches this repo's "don't build for hypothetical scenarios" convention).

This was surfaced to the user as a scope-check rather than silently declared "done" or silently abandoned: extending the base-14 path had hit its real ceiling, and the only way to make further progress on script/bidi fidelity was to reverse the earlier "font embedding deferred until PDF rendering is otherwise end-to-end" decision (`docs/decisions.md`'s base-14 MVP entry, `tasks/pdf-text-shaping-abstraction.md`'s known-gaps list). The user chose to take on font embedding now. See `tasks/pdf-text-shaping-abstraction.md`'s "Real font embedding for the cross-platform path" section for what was built.

**Lesson:** when a planned increment's *mechanism* works in isolation but its *precondition* doesn't hold (here: reordering is correct, but the font can't draw the reordered glyphs anyway), that's worth surfacing as a scope question before shipping it as if it were real progress — a passing test suite doesn't catch "technically correct, practically inert" code.

## Bidi/RTL run reordering revived now that its precondition (real font embedding) holds (2026-07-26, same day)

The user asked what the *original* Windows-only product supported for Hebrew/Arabic/Cyrillic/Greek/CJK in PDF export, since they'd only ever exercised this library with en-US reports. Research (web search on documented SSRS/RDLC PDF-export Unicode support, plus a codebase spike into the original `Microsoft.ReportingServices.Rendering.RichText` Uniscribe pipeline) found the original product had genuine, unconditional support for all five: `TextRun.ShapeAndPlace` shapes every run via Uniscribe regardless of script, `TextLine.ScriptLayout` does real bidi/RTL visual reordering, and `FontPackage`/`CreateFontPackage` does real glyph-subset embedding with an OS/2 `fsType` rights check. Compared against the new cross-platform path's state at the time (real glyph embedding done, per the entry above; bidi reordering still the dead-code revert noted above), the recommendation was: prioritize reviving bidi/RTL reordering first, since it's the only outstanding *correctness* gap for actual script support — Cyrillic/Greek/CJK are LTR and already render correctly once glyphs embed; glyph subsetting and embedding-rights checks are efficiency/compliance concerns, not correctness ones.

The earlier `BidiTextReorderer` attempt (previous entry) was reverted specifically because its precondition — real glyph embedding — didn't hold yet at the time. That precondition is now satisfied (`WriteCompositeText`/`GetOrCreateEmbeddedFont`), so the same class of fix was re-implemented as `BidiRunReorderer` (`Microsoft.ReportingServices.Rendering.RichText/BidiRunReorderer.cs`) and wired into `UnicodeParagraphShaper.Shape`, which now returns runs in visual order rather than logical order. See `tasks/pdf-text-shaping-abstraction.md`'s "Bidi/RTL run reordering for the cross-platform composite path" section for the implementation, scope, and test coverage.

## Embedding-rights check added for the cross-platform composite font path (2026-07-26, same day)

Of the two remaining PDF gaps after bidi/RTL reordering (glyph subsetting, and this embedding-rights check), the user picked the embedding-rights check — smaller and bounded (a single-table byte read) versus subsetting's sfnt-table parse/rewrite. The Win32 composite path already refuses to embed a font whose OS/2 `fsType` forbids it (`FontPackage.CheckEmbeddingRights`, via the Win32 `TTGetEmbeddingType` P/Invoke, needs a real HFONT/HDC) — the cross-platform path had no equivalent and always embedded regardless of `fsType`.

Verified (via a throwaway console probe against the real `SkiaSharp` 3.119.1 package already referenced by this project) that `SKTypeface.GetTableData(uint tag)`/`GetTableTags()` exist and work without any HDC: fetching the `OS/2` table (tag `0x4F532F32`, the big-endian ASCII FourCC — confirmed present in `GetTableTags()`'s output) from a real `SKTypeface.FromFamilyName("Arial")` returned a 96-byte OS/2 table whose byte offset 8-9 (`fsType`) read `0x0008` ("Editable embedding"), matching the OpenType spec's documented table layout. This is the "reading `fsType` straight from `SKTypeface`'s own OS/2 table doesn't need an HDC, so it's possible later" gap noted in the font-embedding entry above — now closed.

`SkiaFontEmbeddingRights.CanEmbed(SKTypeface)` (new file, `Microsoft.ReportingServices.Rendering.ImageRenderer/SkiaFontEmbeddingRights.cs`) reads that table and checks only the `0x0002` "Restricted License embedding" bit — the one `fsType` bit that forbids embedding outright; Preview&Print/Editable/no-subsetting/bitmap-only are usage restrictions for the PDF viewer, not embedding prohibitions, matching what `FontPackage.CheckEmbeddingRights`'s `EMBED_NOEMBEDDING` check already treats as the sole disqualifying case. Wired into `PDFWriter.ProcessFontForFontEmbedding` as a new `pdfFont.SkiaTypeface != null` branch alongside the existing Win32 branch — when a font can't be embedded, `pdfFont.EmbeddedFont` is left `null`, the same state the Win32 path already produces for a non-embeddable font, so every other call site (`WriteSkiaCompositeFont`, the FontDescriptor writer, etc.) needed no changes since they already null-check it.

## Glyph subsetting added for the cross-platform composite font path, without renumbering glyph ids (2026-07-26, same day)

The last remaining smaller PDF gap after the embedding-rights check: the cross-platform composite path always embedded the *whole* font file, unlike the Win32 path's real `FontPackage.Generate`/Windows Font Subsetter-based subset. A full subsetter renumbers glyph ids into a dense range and has to rewrite every glyph-id-indexed table accordingly (`hmtx`, `cmap`, the PDF `/W` widths array, and the glyph-indexed `Tj` hex strings already emitted by `WriteCompositeText`) — a large, correctness-sensitive undertaking.

The chosen approach gets most of the same size win at much lower risk: `TrueTypeGlyphSubsetter` parses `glyf`/`loca`/`head`/`maxp` directly from the raw sfnt bytes and zeroes the outline data of every glyph id not in the document's actual used-glyph set (walking composite-glyph component references so a kept accented letter's base+diacritic components are never dropped), **without renumbering any glyph id**. Since every id/slot stays exactly where it was, nothing already emitted upstream (the `Tj` hex strings, `CIDToGIDMap /Identity`, the `/W` array) needs to change — the subsetter is a drop-in replacement for the raw font bytes `WriteSkiaEmbeddedFont` was already about to embed. Only `glyf` shrinks; `hmtx`/`cmap`/`name`/`post` etc. are left untouched, so this doesn't match a full subset's file-size reduction, but `glyf` is disproportionately large in a full-Unicode-coverage font (thousands of glyphs), so it captures most of the practical win for the common report case (a handful of glyphs actually used).

Scope is deliberately narrow: only TrueType-outline (`glyf`/`loca`) fonts are handled — CFF-flavored OpenType (`'OTTO'`) and TrueType Collections (`'ttcf'`) fall back to whole-file embedding, and any parse exception does the same, rather than risk shipping a corrupt embedded font. The whole-file checksum (`head.checkSumAdjustment`) and every table's own checksum are recomputed per the OpenType spec so the rewritten binary stays valid — verified by round-tripping the subsetted bytes back through `SKTypeface.FromStream` in tests and confirming glyph count, advance widths (for glyph ids beyond just the kept set, since `hmtx` isn't touched), and a composite glyph's outline all survive intact.

**Lesson:** a "real" version of a technique (full glyph-id renumbering subsetting) and a scoped-down version that achieves most of the same practical benefit (id-stable outline stripping) aren't the same amount of risk or effort — when the scoped-down version is a strict, provably-safe subset of what the full version would do (every kept glyph's bytes are byte-for-byte identical to the original; nothing downstream needs to know subsetting happened at all), it's worth choosing deliberately rather than defaulting to the "real" implementation out of a sense that it's more complete.

## Decision: patch CFF DICT operand offsets in place, not re-serialize the whole Top DICT (2026-07-27)

Extending glyph subsetting to CFF-flavored fonts (`CffGlyphSubsetter`) hit a complication TrueType's `glyf`/`loca` subsetting didn't have: CharStrings isn't the last structure in a CFF file — Private DICT (+ Local Subrs), charset, and Encoding normally follow it, each referenced by an absolute-offset operand in the Top DICT. Shrinking CharStrings requires updating those operands. Rather than re-serializing the whole Top DICT (risking corrupting operand encodings the original font used), a minimal DICT tokenizer locates each affected operand's exact byte position and encoding width, then patches the offset in place, reusing the original 3-byte/5-byte integer encoding form. Deliberately narrower than a general DICT writer: only the 3-byte/5-byte forms are patched (the short 1-2 byte forms are never seen holding a real file offset in practice); anything else bails to whole-file embedding rather than risk misencoding it. The same technique was reused for CID-keyed CFF (`PatchCidKeyedStructures`): since a CID-keyed CFF has no single top-level Private DICT (each Font DICT inside the FDArray INDEX has its own, with FDSelect mapping glyph ids to which one governs them), and glyph ids are never renumbered, only FDArray's own position and each Font DICT's Private-offset operand needed the identical delta-patch, parsed with the same DICT tokenizer already used for the Top DICT.

## Decision: extract one TrueType Collection face into a standalone sfnt rather than teach the subsetters about multi-face containers (2026-07-27)

TrueType Collection (`.ttc`) files bundle multiple font faces sharing tables in one physical file (common for CJK system fonts and some Latin families like `cambria.ttc`). Rather than making `TrueTypeGlyphSubsetter`/`CffGlyphSubsetter` TTC-aware, the fix extracts the one face SkiaSharp actually resolved (via `SKTypeface.OpenStream(out int ttcIndex)`, the same face index Skia itself picked for the requested family/style) into a standalone single-face sfnt binary first — reusing the existing table-copy-and-checksum-recompute logic (generalized into `RebuildFontFromDirectory(original, directoryOffset, numTables, replacements)`, with `directoryOffset: 0` for the pre-existing non-TTC callers) rather than adding a new code path. Everything downstream then treats the extracted bytes exactly like an ordinary `.ttf`/`.otf` file, so neither subsetter needed any TTC-specific logic at all.

## Decision: fallback-font retry via `SKFontManager.MatchCharacter`, not a ported version of Uniscribe's fixed script-to-family table (2026-07-27)

The Win32 path's `FontCache.FontFallback`/`ScriptFontMapping` maps real Uniscribe script ids to specific Windows-preinstalled font family names (`"Mangal"`, `"Latha"`, etc.) — neither half translates to the cross-platform path: `UnicodeTextItemizer` never had real Uniscribe script ids to key that table by, and the specific font names aren't guaranteed present on Linux/macOS anyway. `SKFontManager.Default.MatchCharacter(family, style, languageTags, codepoint)` was used instead — it searches every font actually installed on the host and returns one that covers the missing codepoint, which is more robust than a fixed table since it adapts to whatever fonts are really present rather than assuming specific families exist.

## Decision: a hand-rolled, simplified UAX #14 pair-based break-class table instead of embedding `LineBreak.txt` or adding an ICU4N dependency (2026-07-27)

`UnicodeLineBreakAnalyzer`'s original heuristic (break after whitespace or a hyphen) failed CJK text (no spaces) and mishandled non-breaking spaces/glue characters. A byte-for-byte UAX #14 implementation needs the full Unicode line-break property table (30+ classes, thousands of codepoint ranges) or an ICU4N dependency — judged disproportionate to this codebase's other hand-rolled-heuristic increments. Instead, a private `LineBreakClass` enum models roughly 20 of the most consequential classes (mandatory breaks, space/glue/word-joiner, quotes/brackets, punctuation, dashes, digits/currency, CJK ideographs/non-starters) and a `CanBreakBefore(prev, cur)` function applies a subset of UAX #14's pairwise rules. Deliberately not certified-conformant: no locale tailoring (e.g. Japanese kinsoku shori beyond basic gluing), Hangul syllables folded into the CJK `ID` class rather than jamo-aware, and unclassified characters fall back to `AL`.

## Decision: rewrite `RDLValidatingReader` as `XmlReader` composition, not inheritance, to fix CS0618 (2026-07-27)

`Microsoft.ReportingServices.ReportProcessing.RDLValidatingReader` derived from the obsolete `XmlValidatingReader`. It's the active RDL schema validator on the live report-load path (`ReportProcessing.CreateIntermediateFormat` → `ReportPublishing.Phase1` → its nested `RmlValidatingReader` subclass drives the whole parse via `while (m_reader.Read())`), so correctness here is security-relevant (untrusted report XML), not just a style fix.

Fixed by mirroring an already-migrated sibling class of the identical name in a different namespace (`Microsoft.ReportingServices.ReportPublishing.RDLValidatingReader`): wrap an inner `XmlReader` instead of inheriting. The wrinkle that sibling didn't have: this class's real subclass calls `base(textReader, targetRDLNamespace)` first, then mutates `base.Schemas`/`base.ValidationEventHandler`/`base.ValidationType` *afterward*, before the first `Read()` — but `XmlReader.Create(reader, settings)` fixes its settings at construction, with no equivalent post-hoc mutation point. Solved by deferring the real validating `XmlReader`'s construction until first use (a `Reader` property backed by `m_reader ?? (m_reader = XmlReader.Create(...))`), keeping `Schemas`/`ValidationEventHandler`/`ValidationType` mutable via a held `XmlReaderSettings` right up until then. The subclass itself needed zero changes.

**Naming trap:** three distinct RDL-validation classes are easy to conflate — `ReportProcessing.RDLValidatingReader` (this one, on the live load path), the separately-implemented `ReportPublishing.RDLValidatingReader` (already modern, used only by the report-publish-to-server path), and `ReportProcessing.RdlValidator` (no "ing" — a third, unrelated, already-modern validator used by `RdlObjectModel.Serialization/RdlReader.cs`). Confirm which one is actually on the call path before assuming a fix in one covers the others.

## Decision: rewrite `Graphics.NewPage`'s raster surface as portable `Bitmap`, not raw Win32 HBITMAP interop (2026-07-27)

`Microsoft.ReportingServices.Rendering.ImageRenderer.Graphics.NewPage` (the per-page raster surface behind BMP/GIF/JPEG/PNG/TIFF — `LocalReport.Render("IMAGE", ...)`) used to build its bitmap via a raw Win32 sequence: `GetDC(IntPtr.Zero)` → `CreateCompatibleDC` → `CreateDIBSection` → `SelectObject` → `Graphics.FromHdc`, then `Save` recovered a `Bitmap` from the raw HBITMAP via `Image.FromHbitmap`. Empirically confirmed (throwaway WSL scratch test, not committed) to throw `DllNotFoundException` for `user32.dll` on the very first `GetDC` call — before any drawing or text — on every page, for every raster format including TIFF.

Fixed by replacing the whole HBITMAP construction with `new Bitmap(width, height, PixelFormat.Format32bppRgb)` + `Graphics.FromImage(...)`, keeping the `Bitmap` itself (`m_pageBitmap`) as the field `Save`/`EndReport`/TIFF's multi-frame `SaveAdd` operate on directly, instead of round-tripping through a raw `IntPtr` handle. This is the same construction `GraphicsBase.EnsureGraphics` already used for its own scratch HDC, and the same shape Chart's `IRenderSurface`/`GdiRenderSurface`/`SkiaRenderSurface` model (construct a raster surface, draw into it, encode to a stream) — see `docs/rendering-abstractions.md`.

**`Format32bppRgb`, not `Bitmap`'s default `Format32bppArgb`, is load-bearing:** the old HDC-backed surface had no real per-pixel alpha channel. Using the default true-alpha format changed edge-pixel compositing enough that `SunburstChartRdlTests`'s pixel-diff baseline (which renders through this exact path via `IMAGE`/PNG) failed by 14 of 145,152 pixels — all at anti-aliased text-glyph edges, confirmed by inspecting the diff image. `Format32bppRgb` restored the previous, opaque-composite behavior exactly (0 pixel diff after that one-line change) — this class of "true-alpha vs. legacy-opaque-surface" mismatch is worth checking first if any future GDI+ surface swap causes small pixel-diff regressions in a chart/text-heavy baseline.

**This did not make the IMAGE renderer cross-platform — it only removed the first of two blockers.** Re-running the same empirical WSL check after the fix (via the now-committed `ImageWriterRdlTests.SimpleTextbox_RendersToTiff`) shows the crash moved, not disappeared: `new Bitmap(...)` itself now throws for `gdiplus.dll`/`libgdiplus`, landing on the already-documented "GDI+ can't construct any `System.Drawing` object at all on Linux" wall (the Phase 0 spike finding, `docs/platform-support.md`) that already blocks Gauge and Map. A genuine cross-platform TIFF path needs a Skia-backed surface, not just the removal of raw Win32 P/Invokes — tracked as still-open scope in `tasks/image-renderer-cross-platform.md`.

## Decision: classify unknown font families for base-14 fallback by name-substring heuristic, not a real metrics lookup (2026-07-27)

The base-14 fallback path (used only when `EmbedFonts == FontEmbedding.None`) previously mapped every unrecognized font family to Helvetica regardless of whether the real font was serif or monospaced. `ClassifyFallbackBase14Family` instead checks the family name against common serif (`"Georgia"`, `"Cambria"`, `"Garamond"`, `"Palatino"`, ...) and monospace (`"Consolas"`, `"Menlo"`, `"Lucida Console"`, ...) name substrings, falling back to Times-Roman/Courier's own style-suffix spelling — still a name-only heuristic, not a real font-metrics lookup, judged sufficient since this fallback path is only reachable when font embedding is explicitly disabled.

## Discovery: Chart/Gauge model classes could not even be *constructed* on Linux, independent of any rendering-backend work (2026-07-28)

While investigating why chart content never reaches the page for the IMAGE renderer on Linux (see `tasks/image-renderer-cross-platform.md`'s Phase 2 note), traced the actual exception (previously silently swallowed by `DynamicImageInstance.GetImage`'s catch-and-placeholder handling — see below) back to something far more fundamental than a rendering-backend gap: `Chart`'s default constructor builds a default `Title` (`noDataMessage`), whose `private Font font = new Font(...)` **field initializer** runs unconditionally — and `System.Drawing.Font` construction itself requires GDI+, which cannot construct anything at all on Linux under .NET 10, even with libgdiplus installed (the Phase 0 spike finding above). This is not a Skia-migration gap; it means **merely instantiating a `Chart`/`Legend`/`Axis`/`Series`/etc. object crashed immediately on Linux**, before any rendering, Skia or otherwise, was ever attempted. `new Chart()` failed inside `Title..ctor` failed inside `ChartPicture.GetDefaultFontFamilyName()`'s `FontFamily.Families` call (a *second*, independent GDI+ touchpoint) or later inside `Legend`/`Axis`/`Series`'s own eager `Font` fields, depending on construction order.

This directly contradicts this doc's own "Chart rendering (2D/3D): Yes Yes" and "Gauge rendering: Yes" claims elsewhere — those were evidently never re-verified end-to-end on a real Linux environment after whatever change (likely a `System.Drawing.Common`/`Windows.Win32.PInvokeGdiPlus` shim version bump under .NET 10) made `FontFamily`/`Font` construction newly, unconditionally throw instead of silently degrading. A fresh WSL run of `VisualRegressionTests` showed 107 of 137 tests failing this way — the vast majority via exception, not pixel diff.

**Fix (partial, verified): make every such field initializer lazy instead of eager.** `private Font font = new Font(...)` → `private Font font;` + the property getter becomes `return font ??= new Font(...)`, mirroring the "defer GDI+ construction until first real use" pattern already established this session (`GraphicsBase`'s deferred `Graphics`, `Renderer.ImageResources`'s lazy `Dictionary<string, Bitmap>`, `Graphics.GetGdiImageEncoders`'s lazy static field). Applied across `Title`, `Legend` (two fields), `ChartPicture`, `Axis`, `Label`, `Series` (via `DataPointAttributes.Font`'s two `series.font` reads, plus removing an eager `SetAttributeObject(CommonAttributes.Font, new Font(...))` call in `DataPointAttributes.SetDefault`), `Annotation`, `FinancialMarker`, `LegendCellColumn`, `StripLine` (Chart engine); `CustomLabel`, `GaugeLabel`, `LinearLabelStyle`, `LinearPinLabel`, `NumericIndicator`, `State`, `StateIndicator` (Gauge engine — Windows-only rendering regardless, fixed anyway for construction-time consistency). Also guarded `ChartPicture.GetDefaultFontFamilyName()`'s `FontFamily.Families`/`FontFamily.GenericSansSerif` calls to Windows-only, returning a hardcoded name on non-Windows (the exact string doesn't matter — `SkiaCachedFont` already falls back to `SKTypeface.Default` when unresolvable).

**This fix is real but only partial — object construction no longer crashes, but rendering that actually needs a default (never explicitly set) Font still does.** After the fix, `SimpleBarChart_RendersViaSkia_MatchesBaseline` progresses all the way from `new Chart()` through `ChartPicture.Paint`/`Resize`/`CalcLegendPosition` before failing at `Legend.GetOptimalSize` → `Legend.Font`'s *lazy* getter — which still constructs a real `Font` the first time anything actually needs to measure legend text. This is the crux: `System.Drawing.Font` cannot be constructed on Linux **at all**, lazily or not, so any code path that genuinely needs a live `Font` instance (as opposed to merely storing/passing one through) is permanently blocked here — the same category of wall as EMF/Metafile export, not a bug fixable by more laziness. A real fix would need `Legend.GetOptimalSize` (and any similar measurement call site) to call `IDrawingResourceFactory.CreateFont(familyName, size, ...)` directly — which builds an `IChartFont` without ever touching `System.Drawing.Font` — instead of reading the model's concrete `Font` property and wrapping it after the fact; that requires the caller to know it's using an *unset* default (not a user-supplied `Font`) and route around the property entirely, a larger, not-yet-scoped change. WSL verification after this fix: `VisualRegressionTests` improved from 29/137 to 30/137 passing (most remaining failures now hit this same `Legend`/text-measurement wall rather than crashing at construction) — a real but modest improvement; see `tasks/chart-default-font-cross-platform.md` for the remaining scope.

**Also found and left alone:** `DynamicImageInstance.GetImage`'s `catch (Exception) { return CreateExceptionImage(exception); }` — a deliberate "don't crash the whole report if one chart fails" safety net — itself calls `CreateExceptionImage`, which is *also* 100% GDI+ (`new Bitmap`, `Graphics.FromImage`, `Pen`, `Brush`, `Font`) and *also* silently fails on Linux (its own inner catch swallows the failure and returns `null`). This is why the missing chart never surfaced as a visible crash anywhere in this session's testing — two layers of graceful-degradation-by-design each independently absorbed a GDI+ failure, leaving a blank space with no diagnostic at all. Left as-is (correct defensive design in principle; just doubly blind on this platform) rather than expanding scope further this session.
